# The demo bundle

Postgres, Keycloak and one STAMP process, with an example policy set that
exercises every path the product claims: a stateless `check`, a `decide` that
waits for two approvers, a velocity limit fed by an event stream, a policy
authored through the API the console calls, and the same set exported to files
and applied back unchanged.

**Run it with `scripts/quickstart.sh`.** That script is the procedure;
[`docs/quickstart.md`](../../docs/quickstart.md) explains it. This file
documents the bundle's shape — what is in it, why, and what it deliberately is
not.

```
deploy/demo/
  docker-compose.yml         the default profile: no broker
  docker-compose.kafka.yml   the optional Kafka overlay
  keycloak/                  the demo realm, imported at first start
  policies/                  the example policy set, in the file authoring format
  .env                       generated, untracked, per installation
  .run/                      cookie jars, timings, verification output
```

## Two profiles, one policy set

The default profile has **no broker**. Velocity events arrive over the HTTP
ingest route, which every install has, and the limit works exactly as it does
with Kafka in front of it. That is the point of D11's ingestion port: the
aggregation logic can be tested with no broker at all, and the demo can leave
one out.

The overlay adds Kafka and moves the source's `adapter` from `http-ingest` to
`kafka`. Nothing else changes — not a policy, not a schema, not a route, not a
client — which is the claim the port was introduced to make, and the reason the
quickstart is run against both profiles in CI. The two must reach the same deny.

```sh
scripts/quickstart.sh                  # default
scripts/quickstart.sh --profile kafka  # overlay
```

## No credential is shipped

Every credential the bundle needs — the database password, the Keycloak admin
password, the demo users' password, and the two client secrets — is generated by
`scripts/quickstart.sh` into `deploy/demo/.env`, which is not tracked. The realm
file names them as `${PLACEHOLDER}`s that Keycloak's realm import resolves from
the environment at start, and the audit checkpoint signing key is generated
inside the `state` container on first `up`.

So `docker compose up` before the script has ever run fails, naming the script.
That is deliberate, and it is this bundle's whole answer to the requirement that
a demo credential must not start a non-demo deployment: **there is no demo
credential in this repository to start one with.** See
[`docs/security.md`](../../docs/security.md) for the reasoning and for the
residual risk that answer leaves.

## Identities

The realm gives its users and service accounts explicit, readable `sub` values,
because STAMP records an approval under the `sub` of the verified token and
compares a policy's approver list against it. A realm with random UUID subjects
would force the example policies to name UUIDs.

| Identity | Kind | Standing |
|---|---|---|
| `ann` | person | approver, operator; `stamp_capabilities: [policy.author, audit.read]` |
| `bob`, `cid` | people | approvers; no capabilities, which is the fail-closed default |
| `dana` | person | the subject the example decisions are about; no standing at all |
| `svc-pep` | workload | the PEP: calls `check` and `decide` |
| `svc-ingest` | workload | writes velocity events; scoped by `STAMP_INGEST_CREDENTIALS`, not by anything in its token |

`ann` is the only one who can author policy or read the audit views. `bob` and
`cid` can approve and can see their inbox and nothing else — which is worth
seeing, because "authenticated" and "entitled" are separate questions and the
export gate in particular is fail-closed per caller.

## The example policies

Three policies over two resources, deliberately disjoint so that each one
answers exactly one shape of request.

| Policy | Answers | Shows |
|---|---|---|
| `routine-transfer` | domestic transfer under 10,000, account under its daily total | the allow path, and the velocity limit that closes it |
| `high-value-transfer` | domestic transfer of 10,000 or more | a quorum challenge: 2 of `ann`, `bob`, `cid` |
| `ledger-export` | exporting a ledger | a delegated MFA challenge (step-up, D26) |

The quickstart's authoring step adds a fourth, `offshore-transfer`, through the
API the console's form builder calls — which is why the file set leaves offshore
destinations out. Before that revision an offshore transfer is denied outright;
after it, the same request is a decision waiting on two approvers. That change
in the answer is the end-to-end proof, and it is the only one worth having.

The velocity source is a good example of the split R35 draws. The schema names
`transferred_today`, its one parameter and its return type; the metric, the
window, the bucket width and the ingestion adapter are `STAMP_STREAM_SOURCES` on
the deployment. An author who could write those could point a limit at another
tenant's metric or widen its window until the limit stopped biting.

## The delegated MFA challenge completes, end to end

`ledger-export` carries an `mfa` challenge, and the quickstart drives the whole
round trip: the decision goes pending and its response carries the address to
send the subject to, the browser signs in at the demo IdP, the IdP redirects back
to this challenge's own callback path, STAMP redeems the authorization code and
judges the ID token, and the decision resolves. Nothing is stubbed and no step is
skipped past the login form.

Three things make it work, and each of them was a seam that was missing:

1. **The authorization URL is published.** `decision.ChallengeView` carries
   `authorization_url`, answered by the handler through the optional
   `challenge.Viewer` interface so that the decision layer still does not import
   a challenge kind. The stored detail does not travel: the handler names the one
   field that may leave, and the correlator, the nonce and the PKCE verifier are
   not among them.
2. **The redirect has somewhere to land.** `GET /decisions/{id}/challenges/{n}/mfa`
   receives the IdP's redirect, hands `code` and `state` to the challenge through
   the optional `challenge.Redeemer` interface, verifies the ID token that comes
   back against the pinned issuer set, and submits it. The existing `POST` route
   stays: the CIBA client hands its token back that way.
3. **The request carries PKCE.** `stamp-stepup` is registered as a public client
   with `pkce.code.challenge.method: S256`, and Keycloak reads that as a
   requirement — an authorization request without `code_challenge_method` comes
   back as `error=invalid_request` before any login form is shown. The verifier
   is minted at issue and lives on the challenge row, which is where the
   correlator and the nonce already live.

**`state` is not the correlator.** The callback path already names the decision
and the ordinal, so `state` has one job — proving the redirect answers a request
this deployment made — and a fresh random value does it. The correlator stays on
the challenge row and never reaches an address bar, a referrer or a browser
history entry. The landing page the subject reads carries
`Referrer-Policy: no-referrer` for the same reason: the URL it is served at has an
authorization code in its query.

**What is deliberately not demonstrated is CIBA.** D26 settled that: Keycloak's
CIBA grant needs a decoupled authentication server it does not ship, so the CIBA
client stays a contract verified against a mock OP and the demo redirects.

## What this bundle is not

It is not a hardening baseline and it is not a deployment template. Plaintext
OIDC, a Keycloak in dev mode, a broker with no ACLs, a database on tmpfs, a
signing key on a shared volume, and an audit checkpoint every ten seconds are
all choices that make a demo legible and would be defects in production.
[`docs/security.md`](../../docs/security.md) lists them one by one against what
a real deployment does instead. For anything beyond a laptop, start from the
chart in [`deploy/helm/`](../helm/) rather than from this compose file.
