{{ if $apiTier -}}
GOVERNANCE IS NOT LOCKED YET. Two steps, in this order.

1. Take the bootstrap token.

   On its first start the tier holding the api role installs the reserved
   governance policy and prints a one-time bootstrap token. It is shown once,
   on stdout, and stored only as a digest — no later start reprints it, and no
   API returns it.

     kubectl -n {{ .Release.Namespace }} logs deploy/{{ $apiTier }} | grep -A2 'bootstrap token'

   If the pod has already restarted and the log has rotated away, the token is
   gone. Recovery is `stamp breakglass`, which refuses to run while the service
   is up — see docs/break-glass.md.

   Until governance is locked the deployment is in solo-admin mode: whoever
   holds this token can change policy alone. An unused token raises a critical
   audit warning on a timer for exactly that reason.

2. Lock governance as soon as the approver set is known.

     kubectl -n {{ .Release.Namespace }} port-forward svc/{{ $apiTier }} {{ .Values.listeners.console.port }}:{{ .Values.listeners.console.port }}

     stamp policy lock \
       --api http://localhost:{{ .Values.listeners.console.port }} \
       --token "$YOUR_OIDC_ACCESS_TOKEN" \
       --bootstrap-token "$BOOTSTRAP_TOKEN" \
       --threshold 2 --approvers alice,bob

   The console does the same thing from Governance -> Lock. The lock survives
   every authoring mode: `{{ .Values.authoring.mode }}` does not close it, because an operator
   who closed the console's authoring must still be able to leave solo-admin.

   After the lock, a governance revision needs {{ default "the configured" .Values.governance.minApprovers }} approvals or more.
   A threshold larger than the approver set is refused before it is sent — a
   quorum nobody can satisfy is a permanent lockout, not a strict policy.

{{- if eq .Values.topology "split" }}
The split topology has one thing left to wire by hand: the console tier has to
be told where the api tier is, because the bundle reads its API base address
from the operator and from nowhere else (R50). Set

  console.apiBaseUrl: https://<the address your api tier is published at>

to the address a *browser* can reach, not the in-cluster Service name — the
call is made by the approver's browser, and the CSP on every console response
names that origin and the IdP and nothing else.
{{- end }}

Health: every bound listener answers GET /healthz and GET /readyz. /healthz is
the liveness signal and consults nothing, so a 200 there means a process that is
running and not a deployment whose database is reachable. /readyz is what the
readinessProbe asks, and it answers 503 until the database has reached the
schema this image's queries are written against.

Schema before traffic: only the tier holding the api role migrates, and `helm
upgrade` rolls every Deployment at once. A serving pod on the new image must not
take traffic before the schema reaches the version that image needs — every read
it issues would name a column the database does not have yet. /readyz is what
enforces that, so an upgrade that appears stalled with pods Running but not
Ready is usually the migration not having landed:

  kubectl -n {{ .Release.Namespace }} get pods -l app.kubernetes.io/instance={{ .Release.Name }}
  kubectl -n {{ .Release.Namespace }} logs deploy/{{ default "the api tier" $apiTier }} | grep -i schema

Two things follow. Do not point the readinessProbe back at /healthz: that is
what this chart used to do, and it is what let a pod serve errors during an
upgrade. And an image older than this chart does not answer /readyz at all — it
404s, the pod never becomes Ready, and the rollout stops with the old pods still
serving. Upgrade the chart and the image together.
